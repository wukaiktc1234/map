## 一、分离原则

### 1.1 核心定义

| 维度 | Product Decision | Architecture Decision |
|------|------------------|----------------------|
| **核心问题** | 系统业务应该是什么？ | 在业务定义确定后，系统应该如何实现与协同？ |
| **关注点** | 业务定义、业务规则、业务流程 | 技术实现、系统设计、技术选型 |
| **决策者** | 产品经理 / 业务负责人 | 架构师 / 技术负责人 |
| **变更成本** | 低（改业务规则） | 高（改技术实现） |

### 1.2 分离边界

```

└─────────────────────────────────────────────────────────────────────┘
```

### 1.3 越界判断标准

| 越界类型 | 判定条件 | 后果 |
|----------|----------|------|
| **Architecture 越界 (偷偷决定 Business Semantics)** | 架构决策中定义了业务概念、业务规则或业务流程 | 业务定义被技术约束绑架 |
| **Product 越界 (涉及实现细节)** | 产品决策中包含了数据库 schema、API 设计、技术选型 | 技术实现被业务规则过度约束 |

### 3.1 DEC-010: 跨域数据所有权

| 字段 | 值 |
|------|-----|
| **决策ID** | DEC-010 |
| **决策标题** | 跨域数据所有权 |
| **分类** | Architecture Decision |
| **核心问题** | 跨域访问应该如何实现？ |
| **决策者** | 架构师 / 技术负责人 |

**当前问题**:  
跨域数据访问存在以下技术选项：

| 选项 | 技术含义 | 优缺点 |
|------|----------|--------|
| **A: 直接访问** | 服务直接访问其他服务的数据库 | 简单但耦合度高 |
| **B: API 访问** | 通过 API 接口访问其他服务的数据 | 标准但性能开销 |
| **C: 事件驱动** | 通过事件同步数据到本地 | 解耦但数据延迟 |
| **D: 混合方案** | 根据场景选择不同方式 | 灵活但复杂 |

**Architecture Decision 内容** (应保留):

1. **技术实现方式**:
   - 跨域数据访问的技术选项分析
   - 各选项的性能、一致性、可用性对比
   - 推荐的技术实现方案

2. **系统设计规范**:
   - 跨域访问的 API 设计规范
   - 数据一致性保证机制
   - 错误处理和重试策略

3. **技术选型决策**:
   - 选择直接访问、API 访问还是事件驱动
   - 数据同步频率和延迟要求
   - 监控和告警机制

**不应包含的业务语义** (应检查):

- ✅ 无业务语义越界：决策文件中只讨论了直接访问、API 访问、事件驱动等技术选项，未涉及业务概念定义
- **结论**: 分离正确，无越界

### 3.3 DEC-013: 裸接口权限

| 字段 | 值 |
|------|-----|
| **决策ID** | DEC-013 |
| **决策标题** | 裸接口权限 |
| **分类** | Architecture Decision（偏向技术实现） |
| **核心问题** | 25 个无 @RequiresPermission 注解的裸接口如何分配权限码？ |
| **决策者** | 架构师 / 技术负责人 |

**当前问题**:  
裸接口权限存在以下技术选项：

| 选项 | 技术含义 | 优缺点 |
|------|----------|--------|
| **A: 统一注解** | 所有接口统一添加 @RequiresPermission 注解 | 标准但工作量大 |
| **B: 配置中心** | 权限码在配置中心动态管理 | 灵活但复杂 |
| **C: 网关拦截** | 在 API 网关统一处理权限 | 集中但性能开销 |
| **D: 混合方案** | 根据场景选择不同方式 | 灵活但复杂 |

**Architecture Decision 内容** (应保留):

1. **技术实现方式**:
   - 权限码分配的技术选项分析
   - 各选项的性能、安全性、可维护性对比
   - 推荐的技术实现方案

2. **系统设计规范**:
   - 权限码的命名规范
   - 权限码的存储和查询机制
   - 权限验证的性能优化

3. **技术选型决策**:
   - 选择注解、配置中心还是网关拦截
   - 权限码的粒度和层级设计
   - 权限变更的生效机制

**可能涉及的业务语义** (需明确):

- ⚠️ 可能涉及业务语义：权限码的分配可能基于业务规则（例如，哪些操作需要权限？）。但问题本身是如何分配权限码，而不是权限码代表什么业务含义。
- **建议**: 明确权限码的业务含义由 Product Decision 定义，权限码的分配由 Architecture Decision 实现。

|----------|----------|------|
| **技术实现方式** | 跨域访问如何实现？ | 直接访问 vs API vs 事件驱动 |
| **技术选型决策** | 使用什么技术栈？ | JWT vs Session，同步 vs 异步事件 |
| **系统设计规范** | API 设计规范？事件设计约束？ | API 版本管理，事件 Schema 演进 |
| **性能与可靠性** | 如何保证系统性能？如何保证数据一致性？ | 缓存策略，限流策略，灾备切换 |

### 5.3 需要两者共同决策的问题

| 问题类型 | Product 职责 | Architecture 职责 | 协作方式 |
|----------|--------------|-------------------|----------|
| **权限管理** | 定义哪些操作需要权限，权限码的业务含义 | 决定权限码的分配机制，权限验证的技术实现 | Product 定义业务规则，Architecture 实现技术方案 |
| **数据所有权** | 定义数据归属（谁是数据的 Truth Owner） | 决定跨域访问方式（直接访问 vs API vs 事件驱动） | Product 定义数据归属，Architecture 实现访问机制 |
| **外部认证** | 定义供应商如何登录（业务规则） | 决定认证机制（Token vs 短信 vs 微信） | Product 定义登录规则，Architecture 实现认证技术 |

## 八、结论

### 8.1 分离现状总结

| Decision | 当前状态 | 需要行动 |
|----------|----------|----------|
| **DEC-001** | 混合了业务定义和实现细节 | 需要拆分 |
| **DEC-004** | 混合了业务定义和实现细节 | 需要拆分 |
| **DEC-010** | 分离正确，无越界 | 无需行动 |
| **DEC-011** | 分离正确，无越界 | 无需行动 |
| **DEC-013** | 基本正确，但需明确业务规则部分 | 需补充业务规则 |
| **DEC-014** | 分离正确，无越界 | 无需行动 |
| **Product/Food/Material 边界** | 分离正确，无越界 | 无需行动 |

### 8.2 最终目标

确保 Product Decision 只关注业务应该是什么，Architecture Decision 只关注系统如何实现，避免越界，提高决策质量和可执行性。

### 8.3 关键成功因素

1. **明确的职责划分**: 产品经理负责业务定义，架构师负责技术实现
2. **有效的协作机制**: 需要两者共同决策的问题，建立明确的协作流程
3. **持续的监督机制**: 定期审查 Decision 的分离状态，及时发现和纠正越界
4. **团队培训**: 确保所有团队成员理解分离原则和检查清单
